PART I — EXECUTIVE SUMMARY
================================================================================

The plan Codex produced is well-structured and architecturally sound in its
direction. The layered refactor (Domain → Services → API → Supabase) is the
right answer for this codebase. The phase sequence is logical in concept.

However, the audit revealed findings that significantly change the plan's
priorities, its phase ordering, and the scope of Phase 2. These are not minor
adjustments — some are production-critical bugs that exist today, and several
of the plan's assumptions about the codebase are factually incorrect.

PRODUCTION STATUS (as of audit date):
  - Admin login: STATUS UNKNOWN — depends on live Supabase having RPCs absent
    from local migrations. If not, admin login is completely broken.
  - Admin PIN change: BROKEN — change_admin_pin RPC exists in migrations but has
    no GRANT EXECUTE statement. Calling it returns a permission error.
  - RLS: COMPLETELY ABSENT — zero policies, zero ENABLE statements across all tables.
  - Edge Function auth: THREE of four functions have zero authentication.
  - Realtime filter contract: BROKEN — filters accepted by useDeparturesRealtime
    are stored in refs and never applied. All clients receive all departure events.

TOP 5 FINDINGS CODEX MUST ACT ON BEFORE ANY REFACTORING:

  1. change_admin_pin RPC (20260508_transactional_admin_pin.sql) has no GRANT
     EXECUTE — admin PIN changes silently fail with a permission error.

  2. Admin PIN is stored plaintext in app_settings AND read by sync-from-sheets
     to derive ALL supervisor PINs. One app_settings read = all credentials exposed.

  3. submit_departure trusts the client-supplied p_actor_role string — any student
     can bypass quota by sending p_actor_role='ADMIN' and source='ADMIN_OVERRIDE'.

  4. The audit trigger (departures_audit_trigger_fn line 217) defaults approved_by
     to 'system' when NULL — cron activations and manual admin approvals are
     indistinguishable in the admin_overrides audit log.

  5. OffCampusSheet constructs timestamps with local new Date() and no timezone
     conversion. Students on devices with non-Jerusalem timezone will record
     departures with wrong times.

PART II — WHAT CODEX GOT RIGHT (confirmed by code — no changes needed)
================================================================================

1. The quota formula is verified identical on client and server:
   Client (src/lib/quota.ts:5): Math.max(1, Math.round((classSize * 3) / 25))
   Server (20260423_unified_departures.sql:319):
     GREATEST(1, ROUND((v_class_size * 3)::numeric / 25))
   These are equivalent. No change needed. Never change one without the other.

2. supabaseClient.ts correctly uses the IApiClient interface as an abstraction.
   The data fetching boundary is mostly clean — pages call api.* methods.
   The violations are narrower than the plan implies (see Part III, Assumption 3).

3. The Dexie offline schema is well-designed with proper version migrations:
   v1 → v2 → v3 with upgrade hooks. The schema includes a departures table
   matching the Supabase schema. This is solid offline-first architecture.

4. The departure lifecycle (submit → approve/reject → active → completed/cancelled)
   is enforced through RPCs and a DB trigger (departures_audit_trigger_fn lines
   186-227 in unified_departures.sql). The state machine is server-enforced.
   Good. Do not move this to the client.

5. pg_advisory_xact_lock(hashtext(v_class_id)) in submit_departure (line 312)
   makes the quota check + insert atomic at the class level. This is a correct
   and sophisticated pattern. Do not simplify it away.

6. sync-from-sheets correctly uses a server-side secret (X-Sync-Secret header
   validated at line 192 of the Edge Function against SHEETS_SYNC_SECRET env var,
   which is fetched from Google Apps Script Properties at runtime — not hardcoded).
   This is the security model the other three Edge Functions need to copy.

7. The 5-minute undo window after checkout (HomePage.tsx line 190) is good UX.
   The cancel_departure flow is correct — it sets status=CANCELLED and retains
   the row for 30 days. Do not change this behavior.

8. The Dexie schema version 3 added the departures table (lines 69-87 of schema.ts)
   matching the unified departures migration. Good alignment. The absenceRequests
   table remains in Dexie but no longer exists in Supabase — this is dead weight
   in the offline schema (see Part IV, Item 8).

PART III — FACTUALLY INCORRECT ASSUMPTIONS IN CODEX'S PLAN
================================================================================

These must be corrected in the plan document before Codex acts on them.


ASSUMPTION A: "RLS policies were not found in the local scan" (Finding 11)
STATUS: Understatement. RLS does not exist at all.
EVIDENCE: All 13 migration files were scanned. There is not a single
  ALTER TABLE ... ENABLE ROW LEVEL SECURITY
  nor any CREATE POLICY statement anywhere.
CONSEQUENCE: With the anon key (bundled publicly in the PWA), any person can:
  SELECT * FROM students — 381 rows with names, IDs, phones, GPS coordinates
  SELECT * FROM departures — complete departure history for every student
  SELECT * FROM admin_overrides — every admin action taken in the system
  SELECT * FROM app_settings — including the plaintext admin PIN
CORRECTION FOR CODEX:
  "Finding 11 must say: 'RLS has never been enabled on any table. There are zero
   ENABLE ROW LEVEL SECURITY statements and zero CREATE POLICY statements in the
   entire codebase. This is not a partial gap — it is a complete absence.
   Phase 2 must build RLS from scratch, not tighten existing policies.
   Enabling RLS without simultaneously creating at least one SELECT policy
   creates a deny-all state that will break the entire system. Every table
   that gets RLS enabled must receive its policies in the same migration,
   applied atomically.'"


ASSUMPTION B: "Many select('*') calls" throughout the codebase
STATUS: Overstated. The real performance problem is different.
EVIDENCE: supabaseClient.ts has approximately 8 select('*') calls. Most are
  intentional — student records have ~15 fields and most are needed. The actual
  worst-case performance problem is not a select pattern:
  DashboardPage.tsx line 181 calls api.getStudents() to load ALL 381 students.
  Lines 194-199 then compute 3 integer counts (ON_CAMPUS, OFF_CAMPUS, OVERDUE).
  This transfers approximately 150KB of JSON to compute 3 numbers. A single
  SQL COUNT(CASE WHEN "currentStatus"='ON_CAMPUS' THEN 1 END) returns 3 numbers
  in under 1ms with zero network overhead.
CORRECTION FOR CODEX:
  "The select('*') finding is largely accurate but misses the far more costly
   pattern: full table loads for client-side aggregation. The most impactful
   single fix in the codebase is adding a get_location_breakdown() RPC
   (DashboardPage line 181). Prioritize aggregation RPCs over projection
   changes in select(*) calls. Student list selects are not the bottleneck."


ASSUMPTION C: "Supabase is imported directly from stores, pages, and components"
STATUS: Misleading. The data boundary is mostly correct.
EVIDENCE: 12 files import supabase directly, but only for two purposes:
  1. Realtime channel subscriptions — which IApiClient intentionally doesn't abstract.
     This is a gray area, not a violation. The hook useDeparturesRealtime.ts IS
     the abstraction layer for departures realtime.
  2. Auth operations in authStore — supabase.auth.signIn/signOut must be called
     directly since auth isn't part of IApiClient.
  Data reads go through api.* correctly in almost every case.
CORRECTION FOR CODEX:
  "The actual violations of the API boundary are:
   - authStore.ts: auth.signIn, auth.signOut, and PIN verification RPCs (by design,
     but should eventually move to an AuthService wrapper).
   - App.tsx line 77: fire-and-forget lastSeen stamping directly (move to a service).
   - DashboardPage.tsx line 222: direct channel subscription for students realtime
     (creates a double subscription — see Part IV, Item 3).
   Pages do NOT make business data calls directly. The boundary is cleaner
   than the plan implies. Focus Phase 4 on the two genuine violations above,
   not on a broad 'all pages bypass the API' characterization."


ASSUMPTION D: "useDeparturesRealtime should actually use the options it receives"
STATUS: The plan understates the severity. This is a broken contract, not a gap.
EVIDENCE: src/hooks/useDeparturesRealtime.ts lines 7-14 define an interface with
  studentId, classId, grade, status, from, to, limit as filter options.
  Lines 28-31 store them in useRef. They are never read in the subscription setup
  (line 42) or in any event callback (lines 43-66). The channel has no filter config.
  Every subscriber — student screens, supervisor screens, admin screens — receives
  every INSERT/UPDATE/DELETE event from the entire departures table.
  This means a student's device receives realtime messages containing student_id,
  class_id, start_at, end_at, reason for every other student's departure.
CORRECTION FOR CODEX:
  "Phase 8 must fix useDeparturesRealtime as a high-priority item, not an
   improvement. The filter API is completely non-functional. The interim fix
   (before auth model makes server-side Postgres Changes filters possible) is
   to apply client-side filtering in each callback before calling the user's
   onInsert/onUpdate/onDelete. This closes the information disclosure without
   requiring auth decisions. Implementation:
     const shouldPassThrough = (row: DeparturePayload) => {
       if (opts.studentId && row.student_id !== opts.studentId) return false
       if (opts.classId && row.class_id !== opts.classId) return false
       return true
     }
   This must happen in Phase 2A, not Phase 8, because it is a privacy violation."

PART IV — CRITICAL BUGS AND SECURITY VULNERABILITIES (new findings)
================================================================================

These are in addition to the findings in v2. All are confirmed by code.


BUG 1: change_admin_pin RPC has no GRANT EXECUTE [CRITICAL — currently broken]

File: supabase/migrations/20260508_transactional_admin_pin.sql
Evidence: The entire file (34 lines) was read. There is no GRANT EXECUTE statement.
The RPC is defined but never granted to any role.

What happens when a user changes their PIN:
  SettingsPage.tsx line 33 → authStore.changeAdminPin() → supabase.rpc('change_admin_pin')
  Supabase returns: { data: null, error: "permission denied for function change_admin_pin" }
  The UI shows: "הסיסמה לא שנתה בגלל שגיאת מערכת" (system error, line 42)

This is a silent production bug. Every admin who has ever tried to change their PIN
has received an error and the change did not happen.

Also found in this migration: the function updates BOTH app_settings (plaintext) AND
auth.users (bcrypt via extensions.crypt). This is intentional dual-storage but
the bcrypt update at line 23 uses extensions.crypt which requires the pg_crypto
extension to be enabled. If pg_crypto is not enabled in the live project, the
function will fail on every call regardless of the GRANT issue.

FIX REQUIRED (add to a new migration or append to the existing one):
  GRANT EXECUTE ON FUNCTION public.change_admin_pin(text, text) TO authenticated;
  GRANT EXECUTE ON FUNCTION public.change_admin_pin(text, text) TO anon;
  -- Verify pg_crypto extension:
  CREATE EXTENSION IF NOT EXISTS pgcrypto;


BUG 2: Admin PIN is the root secret for all supervisor credentials [CRITICAL — design]

File: supabase/functions/sync-from-sheets/index.ts, lines 149-175

The sync function reads the admin PIN in plaintext:
  const { data: pinRow } = await supabase.from('app_settings').select('value')
    .eq('key', 'admin_pin').single()
  const adminPin: string = pinRow?.value ?? '????'

Then constructs every supervisor PIN as:
  supervisorPin: adminPin + code

This means:
  1. The admin PIN is stored in plaintext in app_settings (readable by anyone
     with anon key since RLS is absent).
  2. Supervisor PINs = admin PIN concatenated with a 3-digit code.
  3. Anyone who reads app_settings reads the admin PIN AND can reconstruct
     every supervisor PIN for every class.
  4. When an admin changes their PIN, ALL supervisor PINs change simultaneously.
     CLAUDE.md documents this (section 7): "If Admin PIN changes — all supervisors
     need new PINs. No automatic notification — manual process."

This is not just a security issue — it is an architectural time bomb. Supervisor PINs
are not independent credentials. They are computationally derivable from the admin PIN.

CORRECT DESIGN (for Phase 7 consideration):
  Option A (minimal change): Store supervisor PINs as independent hashed values in
    app_settings.class_pin_{classId} using bcrypt. Admin PIN change no longer
    affects them. Sync generates random codes, stores hashed, sends plaintext once.
  Option B (recommended for Phase 7): Move to Supabase Auth per admin/supervisor.
    Each supervisor has their own Auth account. classId comes from a JWT claim, not
    a PIN suffix. Admin PIN change affects only the admin account.


BUG 3: Audit log cannot distinguish admin from cron actions [HIGH — audit integrity]

File: supabase/migrations/20260423_unified_departures.sql, line 217

The departures_audit_trigger_fn function (lines 186-227) records every departure
status transition into admin_overrides. The approved_by field is set as:
  NEW.approved_by IS DISTINCT FROM OLD.approved_by: uses NEW.approved_by
  But when tick_departures (the pg_cron job) advances APPROVED → ACTIVE,
  it does not set approved_by. The trigger records NULL, which is then stored
  as 'system' via the COALESCE at line 217.

Result: In the audit log, it is impossible to distinguish between:
  - A departure that was manually approved by Admin Moshe
  - A departure that was automatically activated by the cron ticker

Both show approved_by = 'system' or approved_by = NULL in admin_overrides.

FIX: Add a trigger-level actor_source field to admin_overrides:
  actor_source TEXT DEFAULT 'USER' — values: 'USER', 'CRON', 'SYSTEM'
  When approved_by IS NULL and source is the tick function, set actor_source = 'CRON'.
  This requires a new column and migration but does not break existing queries.


BUG 4: OffCampusSheet creates timestamps in local timezone [MEDIUM — data integrity]

File: src/components/student/OffCampusSheet.tsx, lines 82-88

The form constructs timestamps as:
  const startISO = new Date(`${startDate}T${startTime}:00`).toISOString()
  const endISO   = new Date(`${returnDate}T${endTime}:00`).toISOString()

new Date('2026-05-10T09:00:00') interprets the string in the LOCAL timezone
of the device. .toISOString() then converts to UTC.

For a student whose device is set to UTC (a common misconfiguration), a 9:00 AM
departure is stored as 09:00 UTC = 11:00 AM Jerusalem time (UTC+2 in summer).
The departure would be recorded as two hours later than intended.

CLAUDE.md section on Iron Rules states all dates must be Asia/Jerusalem.
This is violated here.

FIX: Use a timezone-aware construction:
  import { zonedTimeToUtc } from 'date-fns-tz'
  const startISO = zonedTimeToUtc(
    new Date(`${startDate}T${startTime}:00`),
    'Asia/Jerusalem'
  ).toISOString()

Or pass a simple local string and parse it server-side as Jerusalem time in the RPC.


BUG 5: Dexie schema retains absenceRequests table after Supabase table removed [LOW]

File: src/lib/db/schema.ts, line 30 (v1 schema), line 41 (v1 stores)

The IndexedDB schema still includes an absenceRequests table. The corresponding
Supabase table was removed in the unified_departures.sql migration. The Dexie table
is never written to (no code inserts into it), but it occupies space in IndexedDB
and creates confusion for future developers.

FIX: Add schema v4 that deletes the absenceRequests store:
  this.version(4).stores({ absenceRequests: null }).upgrade(...)
  The null value in Dexie means "delete this store."


BUG 6: syncEngine DELETE operation is typed but unimplemented [LOW — type safety]

File: src/lib/sync/syncEngine.ts + src/types/index.ts line 162

SyncQueueItem.operation is typed as: 'INSERT' | 'UPDATE' | 'DELETE' | 'RPC'
The sync engine handles INSERT (line 55), UPDATE (line 59), and RPC (line 52)
but has no case for DELETE. Any sync queue item with operation='DELETE' is
silently dropped on the floor — no execution, no error, no retry.

This is not actively used (no code creates DELETE sync queue items), but the type
definition creates an expectation that is not met.

FIX OPTIONS:
  Option A: Remove 'DELETE' from the operation union type. Make it explicit.
  Option B: Add a handler: supabase.from(item.tableName).delete().eq('id', id)
  Recommendation: Option A — deletes should not be in the offline queue because
  they bypass the business logic that soft-deletes via cancel_departure RPC.


BUG 7: normalizeHebrew not applied to search input in studentsStore [LOW — UX]

File: src/store/studentsStore.ts, lines 65-73

The applyFilter function normalizes grade (line 57) and classId (line 61) through
normalizeHebrew() before comparison. But the search filter (lines 65-73) operates
on raw input without normalization:
  s.fullName.toLowerCase().includes(filter.search.toLowerCase())

If a user types a student name using a different apostrophe variant (e.g., typing
with the geresh character ׳ instead of the ASCII apostrophe), names containing
apostrophes will not match. Hebrew names with yud-apostrophe combinations (like
"אברי׳") are especially affected.

FIX: Apply normalizeHebrew to both sides of the search comparison:
  normalizeHebrew(s.fullName).toLowerCase()
    .includes(normalizeHebrew(filter.search).toLowerCase())

THREAT T1: Read entire student database with zero authentication
Severity: CRITICAL — CVSS 9.1 (Network, Low Complexity, No Privileges Required)
Exploitability: Trivial — anon key is bundled in the PWA JavaScript bundle
Attack:

  2. Open DevTools → Sources → find the JS bundle → search for SUPABASE_URL and ANON_KEY

THREAT T2: Read admin PIN and derive all supervisor PINs
Severity: CRITICAL

THREAT T3: Bypass quota — create unlimited approved departures for any student

    break
  }
  Apply same filter to UPDATE and DELETE handlers.

PART VI — ARCHITECTURAL GAPS NOT IN CODEX'S PLAN
================================================================================


GAP 1: The plan has Phase 5 (Services) before Phase 6 (Domain) — wrong order
This is the most consequential ordering mistake. Services IMPORT domain rules:
  - DepartureService.checkoutStudent() calls departureTransitions.canCheckout()
  - DepartureService.approveDeparture() calls quota.calculateQuota()
  - DepartureService.submitDeparture() calls israelDate.toJerusalemTimestamp()
None of these domain functions exist yet if Domain is Phase 6.
Writing services before domain produces either:
  a) Domain logic duplicated inline in services (violates DRY, wrong layer)
  b) Service stubs that must be rewritten in Phase 6 (wasted work)
DIRECTIVE: Swap Phase 5 and Phase 6. No exceptions.


GAP 2: The plan positions Phase 7 (Auth Model) after Phase 2 (RLS) — circular dependency
Phase 2 instructs: "RLS should use auth.uid() or secured claims."
Phase 7 instructs: "Decide how a student is identified."
auth.uid() only exists if students have Supabase Auth accounts. Students currently
have no Auth accounts — they log in with an ID number only. Writing RLS policies
that use auth.uid() for student rows before deciding whether students get Auth
accounts produces policies that will immediately block all student reads.
DIRECTIVE: Move Phase 7 (as a decision document, not implementation) to before Phase 2B.
Phase 2A (fixes that don't need the identity model) can proceed immediately.
Phase 2B (student/departure RLS) waits until Phase 7 resolves the identity question.
