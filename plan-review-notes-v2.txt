SECTION 1 — WHAT CODEX GOT RIGHT (confirmed by code)
================================================================================

1. The layered architecture goal (Domain → Services → API → Supabase) is the right
   direction. The current code has a partial API layer (IApiClient in types.ts with
   two implementations) that proves this pattern is viable here.

2. Phase 2 (Security before performance) ordering is correct. Security gaps are
   severe enough that no performance work should happen first.

3. supabaseClient.ts mixes too many domains — confirmed. ~627 lines covering
   students, departures, events, SMS, analytics, audit, push, recurring absences.

4. authStore mixes too many concerns — confirmed: student login, admin PIN + Supabase
   Auth, supervisor PIN with legacy fallback, lastSeen stamping, push registration.

5. The quota formula match between client and server is confirmed correct:
   Client (src/lib/quota.ts line 5): Math.max(1, Math.round((classSize * 3) / 25))
   Server (migration line 319): GREATEST(1, ROUND((v_class_size * 3)::numeric / 25))
   They are identical. Do not change either without changing both.

6. syncEngine's raw string execution pattern (tableName/RPC from IndexedDB) is
   correctly identified as a security risk. The plan places the fix in Phase 8;
   see Section 5 below for why it must move to Phase 2.

7. The PR breakdown concept (small reviewable PRs instead of one big-bang commit) is
   correct and must be preserved.

8. Identifying DashboardPage, ExceptionsPage, ClassSupervisorDashboard, RollCallPage
   as targets for UI splitting is accurate. Line counts: 794, 783, 827, 527.

SECTION 2 — CRITICAL BUGS THAT MUST BE FIXED BEFORE THE REFACTOR STARTS

--- BUG 1: Admin and Supervisor login is currently broken [CRITICAL] ---

File: src/store/authStore.ts

Admin login flow (lines 63-75):
  Line 65: supabase.rpc('verify_admin_pin', { p_pin: pin })
  Line 68: supabase.auth.signInWithPassword({ email: 'admin@yeshiva.local', password: pin })

Supervisor login flow (lines 77-98):
  Line 79: supabase.rpc('verify_supervisor_pin', { p_pin: pin })
  Line 91: supabase.rpc('get_admin_pin_length')

The three RPCs called:
  - verify_admin_pin
  - verify_supervisor_pin
  - get_admin_pin_length

These do NOT exist in ANY migration file. All 13 migrations were checked. None of
these function signatures appear. Supabase returns {data: null, error: "function X
does not exist"}. Since null is falsy, line 66 "if (!valid) return false" always
triggers. Admin login always fails silently. Supervisor login always falls through
to the legacy string parsing fallback at lines 89-97.

This is a production bug. The system is not usable for admins unless these functions
exist in the live Supabase project but are absent from the local migration files.

Codex's plan (Phase 7) mentions "verify_admin_pin RPC" as if it exists and only
needs security hardening. It does not exist in the codebase.

DIRECTIVE TO CODEX:
"Add an emergency Phase -1 (or first action in Phase 0) to investigate whether
verify_admin_pin, verify_supervisor_pin, and get_admin_pin_length exist in the
LIVE Supabase project (they are absent from local migrations). If they exist live
but not locally, add their SQL to a migration file immediately to close the gap.
If they don't exist live, admin login is broken in production and must be the
first thing fixed, before anything else. This is not a refactoring task — it is
a production incident."


--- BUG 2: Any user can bypass quota with a single API call [CRITICAL] ---

File: supabase/migrations/20260423_unified_departures.sql, line 287

```sql
IF p_source = 'ADMIN_OVERRIDE' AND p_actor_role NOT IN ('ADMIN', 'SUPERVISOR') THEN
  RETURN jsonb_build_object('error', 'unauthorized', ...);
END IF;
```

The p_actor_role check trusts the CLIENT-SUPPLIED string. There is no server-side
verification of who is calling. Any student can execute:

```javascript
await supabase.rpc('submit_departure', {
  p_student_id: anyStudentUUID,
  p_start_at: startTime,
  p_end_at: endTime,
  p_source: 'ADMIN_OVERRIDE',
  p_actor_role: 'ADMIN',       // client supplies this — server trusts it
  p_force_pending: false
})
```

Result (migration line 323-326): the quota check is entirely skipped, the departure
is inserted with status='APPROVED' immediately, for any student UUID the attacker
chooses to supply, without any approval flow.

Codex's plan says "Remove anon access from sensitive RPCs" but does not identify
this specific attack path. Removing anon access still allows any authenticated user
(any student who logged in) to do this.

DIRECTIVE TO CODEX:
"In Phase 2, add a high-priority action item:
'Replace the p_actor_role parameter trust in submit_departure (line 287 of
20260423_unified_departures.sql) with server-side session verification.
The fix depends on the auth model decision in Phase 7, but the vulnerability
must be acknowledged now. Interim fix options:
  Option A: Require a separate admin session token signed by the server,
            validated in the RPC body.
  Option B: Move source=ADMIN_OVERRIDE into a separate admin-only RPC
            (admin_submit_departure) that is only GRANTED to service_role,
            and remove ADMIN_OVERRIDE from the public submit_departure RPC.
  Option C (recommended): After Phase 7 sets up auth, use auth.jwt() claims
            to verify role inside the RPC, not a client parameter.
Until Option C is available, Option B is the safest interim fix.'"


--- BUG 3: notify-admin-quota-full allows anyone to register as admin [CRITICAL] ---

File: supabase/functions/notify-admin-quota-full/index.ts, lines 75-87

```typescript
if (body.action === 'register') {
  const { pushToken, deviceId } = body as RegisterPayload
  // No authentication check anywhere before this line
  const { error } = await supabase
    .from('app_settings')
    .upsert({ key: `admin_push_token_${deviceId}`, value: pushToken }, ...)
```

Any caller — student, anonymous user, attacker — can POST:
```json
{"action": "register", "pushToken": "attacker-vapid-endpoint", "deviceId": "spy-device"}
```

Their device will then receive every admin notification sent by notify-admin-quota-full,
including: which students are requesting departures, departure IDs, quota status,
and admin decision alerts. This is information exfiltration, not just push spam.

DIRECTIVE TO CODEX:
"In Phase 2, action item for notify-admin-quota-full:
'The 'register' action must require a server-verified admin session before storing
a push token. Options:
  Option A: Require the same SHEETS_SYNC_SECRET-style header with an admin secret.
  Option B: After Phase 7, require a Supabase Auth JWT with admin role claim.
  Interim fix: add a SECRET header check identical to sync-from-sheets. Store the
  admin registration secret in Supabase Edge Function Secrets, not in source code.
This must be in Phase 2A (the immediate security sprint), not Phase 7.'"


--- BUG 4: createEvent() has a silent data inconsistency path [MEDIUM] ---

File: src/lib/api/supabaseClient.ts, lines 386-394

```typescript
const { data: event, error } = await supabase.from('events').insert([...]).select().single()
if (error) throw error
// Lines 391-394: update student status — NO error handling
supabase.from('students')
  .update({ lastSeen: now, currentStatus: newStatus })
  .eq('id', eventData.studentId)
  // ← No .catch(), no await, fire-and-forget
```

If the network drops between the event INSERT and the student UPDATE, the CHECK_IN
event is recorded but the student's status stays OFF_CAMPUS. The event log and the
student status become inconsistent. This is a silent bug — no error is thrown, no
toast is shown.

DIRECTIVE TO CODEX:
"In Phase 4 (API split), add to the action list:
'Fix createEvent() in supabaseClient.ts to await the student status update and
handle its error. If the status update fails, either roll back the event (if in a
transaction via RPC) or throw and surface the inconsistency to the caller.
Also note: mockClient.createEvent() does NOT update student status at all (see Bug 5),
making offline behavior different from online behavior.'"

SECTION 3 — INCORRECT ASSUMPTIONS IN CODEX'S PLAN
================================================================================

--- ASSUMPTION 1 (WRONG): "RLS is partially done and needs tightening" ---

What the plan implies: Phase 2 says "Enable RLS on sensitive tables" as if RLS exists
but is incomplete.

What the code shows: Not a single `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` or
`CREATE POLICY` statement exists in any of the 13 migration files.
CLAUDE.md line 473 explicitly says: "Supabase Row Level Security (RLS) — currently
all students can read all data."

Consequence: Any user with the public anon key (which is bundled into the PWA and
visible in browser source) can query the entire students table, the entire departures
table, the entire events table, and the entire admin_overrides table.

Corrected statement for Codex:
"RLS does not exist at all. There are zero policies, zero ENABLE statements. Phase 2
must start from scratch. Do not say 'tighten' — say 'build from zero'. Every table
that will have RLS needs both ENABLE ROW LEVEL SECURITY and at least one CREATE POLICY
before any authenticated user can read any row from it."

Note: Enabling RLS with NO policies creates a deny-all state. Every table that gets
RLS enabled must simultaneously get at least a SELECT policy for its intended audience
or all reads will fail. This must be done atomically in migrations.


--- ASSUMPTION 2 (WRONG): "Many select('*') calls are rampant throughout" ---

What the plan says: "There are many select('*') calls in areas such as students,
events, sms_events, admin_overrides, recurring_absences, and v_calendar_departures."

What the code shows: There are approximately 8 select('*') instances in supabaseClient.ts.
Several are intentional:
  - getStudents() (line 24): Student list needs ~12 of 15 fields for the admin table
  - getStudent() (line 41): Single record for student dashboard — most fields needed
  - getStudentByIdNumber() (line 57): Login lookup — most fields needed
  - listDepartures() (line 301): Queries v_calendar_departures view — view already
    defines its own projection

The REAL performance problem is not select('*') — it is client-side aggregation
after loading full datasets. The most egregious example:

DashboardPage.tsx line 181 calls api.getStudents() which returns all 381 students.
Lines 194-199 compute: how many have currentStatus ON_CAMPUS vs OFF_CAMPUS vs OVERDUE.
This is a 3-number count that requires transferring ~381 × 15 fields of JSON to
compute 3 integers that a single SQL COUNT(CASE WHEN ...) would return instantly.

Corrected statement for Codex:
"The priority optimization is not removing select('*') from student list reads —
most fields in those reads are needed. The priority is replacing 3 specific patterns:
  1. DashboardPage loading 381 students to count 3 status buckets → RPC returning counts
  2. ExceptionsPage loading all students + filtering into 3 categories in JS → server grouping
  3. Events/audit reads using select('*') on wide tables with many unused fields
Focus Phase 4 projection work on events, sms_events, admin_overrides, and the
dashboard location breakdown. Student list reads are secondary."


--- ASSUMPTION 3 (MISLEADING): "Pages make direct Supabase calls for data" ---

What the plan implies: UI/stores/pages import supabase and call it directly for data.

What the code shows: Data fetching goes through the IApiClient layer correctly.
Pages call api.getStudents(), api.listDepartures(), api.getDashboardStats() etc.
The actual direct imports exist for two specific purposes:
  1. Realtime channel subscriptions (which IApiClient does not abstract)
  2. Auth operations in authStore (supabase.auth.signInWithPassword, signOut)

Files with direct supabase imports (12 total):
  - App.tsx: lastSeen stamping (fire-and-forget)
  - authStore.ts: auth sign-in, sign-out, RPC calls for PIN verification
  - studentsStore.ts: realtime channel subscription only
  - useDeparturesRealtime.ts: realtime channel subscription (this IS the abstraction)
  - DashboardPage.tsx: realtime channel subscription only
  - ExceptionsPage.tsx: realtime channel subscription only
  - ClassSupervisorDashboard.tsx: two realtime channels
  - RollCallPage.tsx: supabase.functions.invoke for FCM broadcast
  - AuditLogPanel.tsx, HistoryPage.tsx, HomePage.tsx: specific realtime patterns

The data boundary is mostly respected. The violation is narrower than the plan implies.

Corrected statement for Codex:
"The data fetching boundary is mostly clean — pages call api.* methods. The violations
to fix are:
  1. authStore direct supabase calls — move PIN verification and auth flows to a
     dedicated AuthService that wraps supabase.auth (Phase 7)
  2. Realtime channels subscribed directly from pages — centralize through typed hooks
     (Phase 8): useStudentsRealtime(classId?), useDeparturesRealtime(scope), etc.
  3. App.tsx lastSeen fire-and-forget — move to a background service (Phase 5/6)
Do not characterize the entire codebase as bypassing the API layer — most data goes
through it correctly."


--- ASSUMPTION 4 (WRONG): "useDeparturesRealtime is scoped to provide filtering" ---

What the plan implies: Realtime subscriptions "are too broad" and need scoping. The
implication is that the hook needs to be updated to use its options.

What the code shows: src/hooks/useDeparturesRealtime.ts lines 7-14 define an interface
with studentId, classId, grade, status, from, to, limit as filter options. Lines 28-31
store them in useRef. But these refs are NEVER READ during subscription setup or
event handling. Line 42 creates a channel with no filter. Line 47 calls onAnyChange()
for every event regardless of filters.

This means:
  - A student screen passing {studentId: 'abc'} receives ALL departure events
  - A supervisor screen passing {classId: 'כיתה הרב משה'} receives ALL departure events
  - The filter interface is a dead API

Corrected statement for Codex:
"useDeparturesRealtime accepts filter options but silently ignores all of them.
This is not a 'too broad' issue — it is a broken filter contract. Phase 8 must:
  1. Either implement server-side Postgres Changes filters using the filter option
     (Supabase supports `filter: 'class_id=eq.{classId}'` in channel config)
  2. Or implement client-side filtering in the event callback before calling
     onInsert/onUpdate/onDelete
  3. Or rename the interface to not accept filter options if they will never be used
Until this is fixed, all pages receive all departure events, which is both a
performance issue (unnecessary renders) and a privacy concern (student sees events
for other students' departures in the Realtime message)."


--- ASSUMPTION 5 (OMISSION): "The plan does not mention mockClient.ts at all" ---

This was flagged in plan-review-notes.txt. Adding here with code evidence.

mockClient.ts is 726 lines. It fully implements all 28 IApiClient methods. CLAUDE.md
states "Both IApiClient implementations must stay in sync." Every phase that adds,
removes, or changes an IApiClient method must also update mockClient.ts.

Phase 4 (API split) in particular risks breaking mockClient because:
  - New methods added to types.ts will cause TypeScript to error in mockClient.ts
  - The split will change which internal functions handle certain operations
  - If the split introduces new behavior (error handling, projection changes), the
    mock must reflect those changes or offline mode diverges from online mode

DIRECTIVE TO CODEX:
"Add to Phase 4 completion criteria:
'mockClient.ts compiles with zero TypeScript errors and all 28 IApiClient methods
are still implemented. Run both supabaseClient and mockClient through a shared
behavioral test suite to confirm identical outputs for identical inputs.
The behavioral divergence in createEvent (Bug 5 above) must be fixed in this phase.'"

SECTION 4 — SECURITY THREAT MODEL (what the plan's security section is missing)
================================================================================

Codex's Phase 2 lists actions (enable RLS, close grants, secure Edge Functions) but
does not show the actual attack paths. A security phase must be grounded in specific
threats. Here is the complete threat model from the code audit:


THREAT 1: Quota bypass → unlimited approved departures for any student
Severity: CRITICAL
Attack surface: submit_departure RPC (migration line 287)
Attack: POST to /rest/v1/rpc/submit_departure with:
  { p_source: "ADMIN_OVERRIDE", p_actor_role: "ADMIN", p_student_id: <any UUID> }
Result: Departure inserted as APPROVED, bypassing quota check (migration line 323)
Root cause: p_actor_role is a client-supplied string, no server verification
Fix: Remove ADMIN_OVERRIDE from the public submit_departure surface. Create a separate
     admin-only RPC for overrides, GRANTED only to service_role (called via Edge Function).
Phase: Must be in Phase 2A (before auth model is decided — it does not depend on it)


THREAT 2: Read all student data — names, IDs, phone numbers, GPS locations, history
Severity: CRITICAL
Attack surface: All tables (RLS completely absent)
Attack: await supabase.from('students').select('*')  // anon key, no auth needed
Result: Returns all 381 student records with full PII
Root cause: RLS has never been enabled on any table
Fix: Enable RLS + CREATE POLICY for each table, starting with students and departures
Phase: Phase 2B (after auth model decision, since student RLS needs identity model)
Note: Admin-only tables (admin_overrides, app_settings) can enable RLS now without
      waiting for the student identity decision — just allow service_role only.


THREAT 3: Register as admin push notification recipient
Severity: CRITICAL
Attack surface: notify-admin-quota-full Edge Function, line 75
Attack: POST to /functions/v1/notify-admin-quota-full with:
  {"action": "register", "pushToken": "<attacker endpoint>", "deviceId": "spy-123"}
Result: Attacker's device receives every subsequent admin notification, including
        departure request alerts with student names and departure IDs
Root cause: Zero authentication on the register action
Fix: Add an admin secret header check identical to sync-from-sheets SHEETS_SYNC_SECRET
Phase: Phase 2A (trivial to add, massive security improvement)


THREAT 4: GPS location broadcast to all students (privacy violation)
Severity: HIGH
Attack surface: broadcast-location-request Edge Function, lines 19-39
Attack: POST to /functions/v1/broadcast-location-request with empty body
Result: Silent FCM notification sent to all Android students requesting GPS upload
Root cause: Zero authentication
Fix: Add admin secret header check; log every invocation in admin_overrides
Phase: Phase 2A


THREAT 5: IndexedDB injection → arbitrary sync operations on reconnect
Severity: HIGH (requires physical device access or XSS)
Attack surface: src/lib/sync/syncEngine.ts, lines 49-61
Attack: Open DevTools → Application → IndexedDB → syncQueue table →
        Insert: { tableName: 'admin_overrides', operation: 'INSERT', payload: {...} }
        When app reconnects: supabase.from('admin_overrides').insert(payload) executes
Result: With RLS off, inserts arbitrary admin override records; can forge audit history
Root cause: No whitelist on tableName or operation in the sync replay loop
Fix: Whitelist allowed operations: only submit_departure, return_departure,
     cancel_departure, register_push allowed as sync queue entries. Validate on read.
Phase: Phase 2A (security fix, not architectural — add validation before any RLS work)


THREAT 6: Push notification to any known subscription endpoint
Severity: MEDIUM
Attack surface: send-push Edge Function, lines 177-183
Attack: POST to /functions/v1/send-push with:
  { subscription: <any valid push endpoint>, title: "Attack", body: "..." }
Result: Push notification sent to any Web Push subscription URL the attacker knows
Root cause: No authentication on sender; VAPID keys validate the server, not the caller
Fix: Require admin secret header; validate subscription belongs to a known student UUID
Phase: Phase 2A


THREAT 7: Student sees other students' departure events via Realtime
Severity: MEDIUM (information disclosure)
Attack surface: useDeparturesRealtime.ts — channel is global, filter options ignored
Attack: A student subscribes to the departures channel. They receive Realtime messages
        for every other student's departure INSERT/UPDATE/DELETE event, including
        student_id, class_id, start_at, end_at, reason.
Root cause: Supabase Realtime postgres_changes does not apply row-level filtering here;
            client-side filtering is accepted by the hook but never applied.
Fix: Either add server-side Postgres Changes filter (filter: `student_id=eq.{id}`)
     or apply client-side filter in the event callback before calling user's onInsert.
Phase: Phase 8 (after RLS + auth model, since server-side filter needs auth context)
