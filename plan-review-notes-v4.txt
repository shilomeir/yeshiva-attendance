PART II — THE FIVE PRODUCTION BUGS NOBODY CAUGHT (new in v4)

BUG A: approve_departure supervisor check is broken — any supervisor approves anything
File: supabase/migrations/20260423_unified_departures.sql:466–475
Code:
  IF p_actor_role = 'SUPERVISOR' THEN
    IF NOT EXISTS (
      SELECT 1 FROM app_settings
      WHERE key = 'class_code_' || v_dep.class_id
    ) THEN
      RETURN jsonb_build_object('error', 'class_mismatch');
    END IF;
  END IF;

The check asks: "Does A class code exist for this departure's class?" Not: "Is THIS
supervisor the one for this class?" The answer is always YES for every valid class,
so the guard never fires. Any client sending p_actor_role='SUPERVISOR' plus any
p_actor_id can approve departures for any class. This is a complete bypass.

Practical impact: ClassSupervisorDashboard.tsx:189 sends actorId='supervisor'
(a literal string, not a real ID) for every approval. The server accepts it.
There is no per-supervisor authorization anywhere.

Fix:
  -- Create a proper supervisors lookup table (see Part V)
  -- Until then, minimum viable fix: require that a class_code_{class_id} key
  -- exists AND that the calling p_actor_id matches a stored supervisor token.
  -- The current check does only the first half — add the second.


BUG B: sync-from-sheets UPSERT always resets currentStatus to ON_CAMPUS
File: supabase/functions/sync-from-sheets/index.ts:99
Code:
  currentStatus: 'ON_CAMPUS',

The sync function UPSERTs every student with currentStatus: 'ON_CAMPUS'. Supabase's
ignoreDuplicates: false means this column IS included in the conflict update.
Any sync triggered while a student has an ACTIVE departure resets them to ON_CAMPUS
in the DB. The departure row still shows ACTIVE. The tick will try to complete it,
but the student's status is already wrong. This is a silent data corruption on
every sync triggered mid-departure.

Supabase PostgREST upsert with onConflict supports explicit update column lists.
Fix (immediate):
  const { error } = await supabase.from('students').upsert(rows, {
    onConflict: 'idNumber',
    ignoreDuplicates: false,
    // Only update these columns — never touch currentStatus, push_token, fcm_token:
  })
  // PostgREST doesn't support column-level upsert directly.
  // Use a MERGE-style SQL function instead:
  CREATE OR REPLACE FUNCTION sync_student_from_sheet(...)
  AS $$
    INSERT INTO students (..., "currentStatus")
    VALUES (..., 'ON_CAMPUS')
    ON CONFLICT ("idNumber") DO UPDATE SET
      "fullName" = EXCLUDED."fullName",
      grade = EXCLUDED.grade,
      "classId" = EXCLUDED."classId",
      phone = EXCLUDED.phone
      -- currentStatus, push_token, fcm_token, deviceToken: NOT updated
    $$;


BUG C: getClasses() generates phantom IDs that match nothing in the database
File: src/lib/constants/grades.ts:21–25
Code:
  return Array.from({ length: level.classCount }, (_, i) =>
    `${gradeName} כיתה ${i + 1}`)

This generates IDs like "שיעור א כיתה 1", "שיעור א כיתה 2". Real DB classId
values are "כיתה הרב אבישי", "כיתה הרב בועז", etc. (see CLAUDE.md §3).

The result: ALL_CLASS_IDS (used in supervisorAuth.ts:54 to enumerate all classes)
contains entirely fabricated values. The legacy supervisor PIN fallback in
supervisorAuth.ts:22-49 uses these synthetic IDs, so it always sets classSupervisor
to a classId that returns zero students from the DB.

Fix: Remove ALL_CLASS_IDS and getClasses() entirely. Class IDs must come from the
DB at runtime, not from a hardcoded generator that invents them.


BUG D: idNumber correction in Google Sheets destroys all student history
File: supabase/functions/sync-from-sheets/index.ts:137-143 (delete phase)
File: supabase/migrations/20260423_unified_departures.sql:37 (CASCADE)

The sync UPSERT uses idNumber as the conflict key. When a student's idNumber is
corrected (e.g., typo fix: 111222333 → 111222334), the old row does not appear
in the new sheet payload and is hard-deleted with full CASCADE:
  - departures.student_id → ON DELETE CASCADE (line 37) — all departure rows gone
  - admin_overrides.studentId → ON DELETE CASCADE (20260417_cascade_admin_overrides.sql:8)
  - events: survive (departure_id set to NULL) but studentId is orphaned

The new idNumber creates a fresh student UUID with zero history.

Fix: Add a UNIQUE constraint on idNumber to the migrations if it doesn't exist in
the live DB (verify first). Add a dedicated RPC:
  CREATE OR REPLACE FUNCTION correct_student_id_number(
    p_old_id TEXT, p_new_id TEXT
  ) RETURNS VOID LANGUAGE plpgsql AS $$
  BEGIN
    UPDATE students SET "idNumber" = p_new_id WHERE "idNumber" = p_old_id;
  END; $$;
The sync function must NEVER rely on delete+reinsert for a key field change.
If idNumber changes for an existing student (same name, same class), use this RPC.


BUG E: Stuck sync items retry forever — a failed item becomes a retry storm
File: src/lib/sync/syncEngine.ts:5,73
Code:
  const STUCK_RETRY_THRESHOLD = 3  // Only controls UI badge — NOT a cap
  retryCount: item.retryCount + 1  // Increments forever — no deletion

Items above STUCK_RETRY_THRESHOLD are still included in processQueue() and
retried on every cycle (every 30s + every online event + every foreground event).
A permanently invalid item (e.g., created against an old schema) retries
indefinitely. The queue accumulates dead items. No structured error is surfaced,
no dead-letter queue, no user action available to clear stuck items.

Fix:
  const MAX_RETRIES = 10
  const BACKOFF_BASE_MS = 30_000
  // In processQueue():
  if (item.retryCount >= MAX_RETRIES) {
    await db.syncQueue.delete(item.id)
    reportSyncFailure(item)  // structured log + toast
    continue
  }
  // Exponential backoff: only retry if enough time has passed
  const nextRetryAt = item.lastAttemptAt + BACKOFF_BASE_MS * 2 ** item.retryCount
  if (Date.now() < nextRetryAt) continue

FEATURE 1: Supervisor approves departure for another class (cross-class approval)

What needs to change:
  A. src/lib/auth/supervisorAuth.ts:12-15 — ClassSupervisorInfo.classId: string
     Must become classIds: string[] or a permissions object. Single-value today.

  B. supabase/migrations/20260423_unified_departures.sql:466-475 — the broken

  C. The audit log: ClassSupervisorDashboard.tsx:189 passes actorId='supervisor'

     in the audit record to answer "which supervisor approved this foreign class."

  D. The realtime subscription: useDeparturesRealtime.ts:41 creates one channel
     filtered to one classId. Multi-class supervisor needs a subscription that
     covers multiple classes — the filter interface accepts a single classId today.

  E. The UI: ClassSupervisorDashboard.tsx has no class-picker. Single-class
     assumption is baked into every rendered card, every filtered query,
     every "הכיתה שלי" badge.

Total minimum files to change: 7. Under Codex's refactored architecture: same 7,
because the service/domain split doesn't change the authorization data model.


FEATURE 2: Admin moves student between classes from dashboard

What needs to change:
  A. The UI already has ClassEditModal (supabaseClient.ts:71: api.updateStudentGrade).
     So this technically exists. But CLAUDE.md Iron Rule #1 says class edits are
     overwritten by the next sync. The actual problem is making class moves
     survive sync — which requires sync to distinguish "admin set this classId"
     from "sheet originally assigned this classId."

  B. supabase/functions/sync-from-sheets/index.ts:97 — the UPSERT overwrites
     classId on every sync. A student moved by admin will revert on next sync.
     Fix requires: a "manual_class_override" boolean column on students, and
     sync logic that skips classId update when manual_class_override = true.

  C. Quota accounting after the move: departures.class_id (line 42 of the migration)
     is a snapshot frozen at submission time. After a class move, any live
     (PENDING/APPROVED/ACTIVE) departure still counts against the OLD class.
     New class's quota is not affected. Both supervisors see inconsistent data.
     Fix requires: an UPDATE on live departures' class_id when a student moves.

  D. Audit trail: there is no event_type for CLASS_CHANGE. The events.type CHECK
     constraint (src/types/index.ts) would need CLASS_CHANGE added. The
     admin_overrides table has no concept of "previous_value / new_value" pairs
     for attribute changes — it only records departure lifecycle events.

  E. Google Sheets sync: the next sync will still send the OLD class for this
     student (because Sheets is source of truth). The system needs a conflict
     resolution strategy: sheet wins, or manual override wins?

Total minimum files: 8 + new migration for manual_class_override column.


FEATURE 3: Multiple supervisors per class / one supervisor managing multiple classes

This is a COMPLETE ARCHITECTURAL REDESIGN of the authentication system:

  A. The entire supervisor PIN scheme (adminPin + classCode) assumes 1:1 mapping.
     Multi-class requires a supervisors TABLE with UUID PKs, an expiry timestamp,
     a class_ids[] array or a supervisor_classes join table. This replaces all
     app_settings.class_code_{classId} key-value pairs entirely.

  B. supabase/functions/sync-from-sheets/index.ts:36-63 — ensureClassCodes must
     be replaced with a supervisor provisioning system. Today it auto-generates
     3-digit codes on sync. Tomorrow it needs to manage supervisor accounts.

  C. supervisorAuth.ts:22-49 — parseClassSupervisorSuffix must be deleted.
     It constructs classIds as "שיעור א כיתה N" which don't exist in the DB.
     The new PIN system must return a list of authorized classIds from the DB.

  D. authStore.ts:20 — classSupervisor: ClassSupervisorInfo | null must become
     supervisorSession: SupervisorSession | null where SupervisorSession contains:
       authorizedClassIds: string[]
       supervisorId: string  (UUID, not a literal string)
       expiresAt?: number    (for Feature 5 time-window permissions)
       permissions?: PermissionSet  (for Feature 4 per-feature permissions)

  E. Every component that reads classSupervisor.classId must be refactored to
     accept an array or a "selected class" state.

This is not a phase in Codex's plan. It must be. It is at minimum a 3-week effort
and it blocks several other phases.


FEATURE 4: Per-feature permissions (can approve but not see GPS)

  A. src/lib/api/types.ts:43 — actorRole: 'STUDENT' | 'ADMIN' | 'SUPERVISOR'
     Three values, no extensibility. Adding per-feature permissions requires:
       type Permission = 'approve_departure' | 'reject_departure' | 'view_gps'
                       | 'broadcast_location' | 'view_audit_log' | ...
       type ActorGrant = { role: ActorRole; permissions: Permission[] }
     This changes the IApiClient interface, supabaseClient, mockClient, and every
     RPC call that passes actorRole.

  B. The SQL RPCs accept p_actor_role as a string. They would need to accept a
     permission token or verify against a permissions table. This is a DB migration.

  C. The route guards in App.tsx:37-41 check role presence only. They need to
     accept a permission predicate: <RequirePermission perm="approve_departure">.

  D. The UI conditional rendering ("show Approve button only if supervisor") must
     change to check permissions, not role. This affects ClassSupervisorDashboard,
     ExceptionsPage, and every approval-action component.


FEATURE 5: Time-window permissions (night supervisor 21:00-06:00)

  A. SupervisorSession (see Feature 3D above) must include startHour and endHour.
  B. The ClassSupervisorGuard (App.tsx:37-41) must check current time against
     the window. Currently it checks only existence of classSupervisor.
  C. The server-side approve_departure RPC has no time-window check. An expired
     session can still call the RPC because there is no server-side validation.
  D. Requires: server-side session expiry enforcement (JWT claims or DB lookup).

PART V — THE REQUIRED SUPERVISORS TABLE (not in Codex's plan at all)
================================================================================

Every single extensibility problem in Part IV traces back to the same root cause:
supervisors are not first-class entities in the data model. They are PINs in
a key-value store derived from another PIN. The entire supervisor authorization
system is built on a single string in app_settings.

Codex's plan has Phase 7 "New Authorization and Identity Model" — but it frames
this as a decision to be made later, after Phase 2B, after most of the refactor
is complete. This is wrong. The decision must be made NOW because:
  1. Phase 2B's RLS policies for supervisors depend on the identity model
  2. Phase 5/6's service method signatures depend on the permission model
  3. Phase 8's scoped realtime subscriptions depend on the classId being a list
  4. The audit log format depends on supervisors having real IDs

The required table (for Codex to add to Phase 7, moved to before Phase 2B):

  CREATE TABLE supervisors (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    full_name TEXT NOT NULL,
    pin_hash TEXT NOT NULL,           -- bcrypt, replaces derived PIN
    created_at TIMESTAMPTZ DEFAULT now(),
    expires_at TIMESTAMPTZ,           -- NULL = permanent, for Feature 5
    created_by TEXT                   -- admin who provisioned this supervisor
  );

  CREATE TABLE supervisor_classes (
    supervisor_id UUID REFERENCES supervisors(id) ON DELETE CASCADE,
    class_id TEXT NOT NULL,           -- matches students.classId
    can_approve BOOLEAN DEFAULT true,
    can_view_gps BOOLEAN DEFAULT false,
    PRIMARY KEY (supervisor_id, class_id)
  );

  -- Migration from PIN scheme to supervisors table:
  -- Read app_settings WHERE key LIKE 'class_code_%'
  -- For each entry, INSERT a supervisor row with a generated PIN,
  -- INSERT supervisor_classes for the class,
  -- Delete the app_settings key.
  -- Communicate new PINs to supervisors out-of-band.

This is the correct foundation. Building Features 1-5 on the PIN scheme is
building on sand. The supervisor table is a prerequisite for Phase 2B, not
an option for later.

Codex's plan does not mention mockClient.ts once in 828 lines.
CLAUDE.md rule (section 18): "Both IApiClient implementations must stay in sync."

The following divergences were found by direct code comparison.

PART VII — CROSS-CUTTING CONCERNS THE LAYERED REFACTOR WON'T FIX
================================================================================

Codex's layered refactor (Domain → Services → API) is correct as far as it goes.
It doesn't go far enough. The following problems are NOT solved by adding layers —
they require specific architectural decisions that must be made now.


GAP 1: No Domain Event System — side effects are imperative chains

When a departure is approved, the following chain fires in ORDER from supabaseClient.ts:
  1. approve_departure RPC (line 207) — DB: PENDING → APPROVED, DB trigger → admin_overrides
  2. _sendApprovalPush called fire-and-forget (line 217, not awaited)
  3. Second network call to fetch student_id from departure (line 228)
  4. Third network call to fetch push_token from students (line 232)
  5. Edge function invoke 'send-push' (line 238)

Problems with this chain:
  - Step 2 is fire-and-forget. If it fails, there is no error, no retry, no log.
  - Steps 3-4 are 2 extra round-trips fetching data the RPC could have returned.
  - mockClient does none of steps 2-5 (Divergence 4 above).
  - Adding a new post-approval effect (SMS to parent, webhook to external system,
    unlock dorm door) requires editing supabaseClient AND mockClient in a new
    specific place. There is no "register a handler for DepartureApproved."

What should exist:
  // After approve_departure RPC returns successfully:
  eventBus.emit('departure.approved', {
    departureId, studentId, classId, actorId, approvedAt
  })
  // Subscribers register independently:
  eventBus.on('departure.approved', sendApprovalPush)
  eventBus.on('departure.approved', logToExternalAudit)  // future
  eventBus.on('departure.approved', notifyParent)        // future

The event bus can be simple (synchronous, in-process). The key is that adding
a new post-approval side effect requires adding one subscriber, not editing the
service. This is the "open/closed principle" — open for extension, closed for
modification.

DIRECTIVE FOR CODEX: Add to Phase 5 (Services), not as a nice-to-have:
  "Create src/services/events/domainEvents.ts — a typed event bus.
   Every departure lifecycle transition emits a domain event.
   Side effects (push, audit, status update) become subscribers.
   The Service layer emits; the Infrastructure layer (API clients) subscribes."


GAP 2: No Runtime Configuration Layer — 7 critical values are compile-time constants

The following values are hardcoded and require a code redeploy to change:
  gps.ts:5-8: CAMPUS_LAT, CAMPUS_LNG, CAMPUS_RADIUS_METERS, AREA_RADIUS_METERS
  HomePage.tsx:190: 5-minute undo window (5 * 60 * 1000)
  supabaseClient.ts:241: "בוקר טוב! היציאה שלך אושרה, לך בשלום 🎉" push message
  syncEngine.ts:5: STUCK_RETRY_THRESHOLD = 3
  syncEngine.ts: 30-second sync interval (hardcoded in setInterval calls)
  notify-admin-quota-full: push message templates (hardcoded in Deno)

For a system managing the physical location of students at a religious institution:
  - Campus coordinates must be configurable without a redeploy (satellite campus,
    campus expansion, GPS calibration update)
  - Push notification text changes for holidays, new year greetings
  - Retry thresholds tuned per deployment environment

These belong in app_settings with type-safe accessors:
  SELECT value FROM app_settings WHERE key = 'campus_lat'
  SELECT value FROM app_settings WHERE key = 'push_template_departure_approved'

DIRECTIVE FOR CODEX: Add to Phase 3 (Data Model):
  "Designate the following app_settings keys as runtime configuration:
   campus_lat, campus_lng, campus_radius_meters, area_radius_meters,
   undo_window_seconds, push_template_departure_approved, sync_retry_max.
   Add a config service: src/services/config/appConfig.ts that reads these
   at startup and caches them. Components read from the config service, not
   from hardcoded constants."


GAP 3: Realtime is not a singleton — concurrent mounts double callbacks

useDeparturesRealtime.ts:41: const channel = supabase.channel('departures-realtime')
The channel name is hardcoded. If two components mount simultaneously, two channels
with the same name subscribe. Supabase Realtime multiplexes by name — both fire.
Every departure change triggers BOTH callbacks, doubling load calls.

Additionally, 8+ raw supabase.channel() calls bypass the hook entirely:
  DashboardPage.tsx:223 — 'dashboard-students-realtime'
  ExceptionsPage.tsx:651 — 'exceptions-students'
  AuditLogPanel.tsx:76 — 'audit-log-realtime'
  RollCallPage.tsx:121,165,204 — three channels
  studentsStore.ts:190 — 'students-global-realtime'
  ClassSupervisorDashboard.tsx:481,494 — two channels

None of these go through the hook abstraction. Adding a cross-cutting concern to
realtime events (rate limiting, auth check, unified reconnect logic) requires
changing 9 different places.

What should exist: a singleton realtime service with a registry:
  // src/services/realtime/realtimeService.ts
  class RealtimeService {
    private channels = new Map<string, RealtimeChannel>()
    subscribe(table: string, filter: RealtimeFilter, callback: RealtimeCallback)
    unsubscribe(subscriptionId: string)
  }
  export const realtimeService = new RealtimeService()  // module singleton

DIRECTIVE FOR CODEX: Add to Phase 8 (Realtime/Offline):
  "Replace all raw supabase.channel() calls with a singleton RealtimeService.
   The service deduplicates channels by (table + filter) combination.
   useDeparturesRealtime becomes a thin React wrapper around RealtimeService."


GAP 4: Sync queue has no idempotency guarantee

syncEngine.ts:54-56 — INSERT operations use a client-generated UUID as the payload id.
If the INSERT succeeds but the network drops before db.syncQueue.delete(item.id)
runs, the item stays in the queue and is retried with the same UUID. The retry
fires a second INSERT with the same id, which hits a PRIMARY KEY violation.
This increments retryCount. After 3 attempts the item appears in the "failed" count
but is still retried every 30 seconds forever (see Bug E above).

For RPC operations: if submit_departure succeeds but the queue deletion fails,
the student gets a duplicate departure on retry. The GIST EXCLUDE constraint
prevents overlapping departures, so the retry returns an overlap error — the item
is stuck in the queue permanently, and the student's departure is actually correct
in the DB but appears as an error in the queue.

Fix:
  1. For INSERT operations: use INSERT ... ON CONFLICT (id) DO NOTHING so retries
     are safe. This requires the server to accept client-provided UUIDs and the
     client to generate them before queuing.
  2. For RPC operations: pass the SyncQueueItem.id as an idempotency key to
     the RPC. The RPC uses it to de-duplicate: if this key has been processed,
     return the previous result. Store processed keys in a small dedup table
     with TTL.
  3. Add proper dead-letter handling (see Bug E fix).


GAP 5: The 5-minute undo window is a UX illusion

HomePage.tsx:190: setUndoCheckout({ expiresAt: Date.now() + 5 * 60 * 1000 })
This is in-memory React state. It is destroyed on:
  - Page refresh
  - Tab close and reopen
  - PWA killed by OS memory pressure (common on mobile within minutes)
  - Navigation away and back

The cancel_departure RPC has no time window — a student can call it at any time
until the departure is COMPLETED. The "5-minute" limit is entirely client-side
enforcement. If the PWA is killed and reopened, the undo banner is gone but the
departure is still ACTIVE and cancellable.

The product guarantee should be enforced server-side:
  CREATE OR REPLACE FUNCTION cancel_departure(p_id UUID, ...)
  AS $$
  DECLARE
    v_created_at TIMESTAMPTZ;
    v_undo_window INTERVAL;
  BEGIN
    SELECT created_at INTO v_created_at FROM departures WHERE id = p_id;
    SELECT (value::int || ' seconds')::INTERVAL INTO v_undo_window
      FROM app_settings WHERE key = 'student_cancel_window_seconds';
    IF now() > v_created_at + v_undo_window AND p_actor_role = 'STUDENT' THEN
      RETURN jsonb_build_object('error', 'undo_window_expired');
    END IF;
    ...
  END; $$;
The client shows the countdown only when the window is open. It can trust the
server to enforce it. The value comes from app_settings (configurable).

PART VIII — THE CLASS RENAME PROBLEM (silent quota corruption, unaddressed by plan)
================================================================================

This is the most dangerous silent corruption scenario in the codebase.

When Google Sheets renames a class (e.g., "כיתה הרב משה" → "כיתה הרב משה ב"):

Step 1: sync-from-sheets runs. It UPSERTs students with new classId.
Step 2: ensureClassCodes (index.ts:36-63) runs. It creates a NEW class_code entry
        for the new name. It DOES NOT delete the old class_code entry.
Step 3: Students now have classId = "כיתה הרב משה ב" in the students table.
Step 4: BUT: every departure row in the departures table still has
        class_id = "כיתה הרב משה" (frozen snapshot at submission time).

Now the quota check in submit_departure (line 347) does:
  SELECT COUNT(*) FROM departures WHERE class_id = v_class_id AND status IN (...)
  -- v_class_id is resolved from students.classId → "כיתה הרב משה ב"
  -- The old departures have class_id = "כיתה הרב משה"
  -- The COUNT returns 0. The class appears empty. Full quota available.
  -- Multiple students can now depart simultaneously, bypassing quota.

This is a silent, production-level quota bypass triggered by any class rename.
No error is thrown. No log is written. The quota check silently returns wrong
numbers until all old departures expire.

Additionally:
  - The supervisor's dashboard query (api.listDepartures({ classId: 'כיתה הרב משה ב' }))
    returns ZERO results for any departure created before the rename.
    The supervisor has no visibility into ongoing departures during the transition.
  - The orphaned class_code entry for "כיתה הרב משה" remains valid forever (Bug E).
    Any supervisor with the old PIN can still "approve" departures — the broken
    check in Bug A accepts any valid class_code key.

DIRECTIVE FOR CODEX: Add to Phase 3 (Data Model), mark as CRITICAL:

  "The class_id denormalization problem must be addressed with a migration strategy:

   Option A — Cascade UPDATE on rename (recommended):
     CREATE OR REPLACE FUNCTION rename_class(p_old_id TEXT, p_new_id TEXT)
     RETURNS VOID AS $$
     BEGIN
       UPDATE students SET \"classId\" = p_new_id WHERE \"classId\" = p_old_id;
       UPDATE departures SET class_id = p_new_id WHERE class_id = p_old_id;
       UPDATE app_settings SET key = 'class_code_' || p_new_id
         WHERE key = 'class_code_' || p_old_id;
     END; $$ LANGUAGE plpgsql;
     -- Call this from sync-from-sheets when a class name changes.
     -- Detect renames by matching student count and grade between old and new names.

   Option B — Classes table as FK target:
     CREATE TABLE classes (
       id TEXT PRIMARY KEY,  -- the class name IS the id (matches existing design)
       grade TEXT NOT NULL,
       display_name TEXT,
       created_at TIMESTAMPTZ DEFAULT now(),
       retired_at TIMESTAMPTZ  -- instead of deleting renamed classes
     );
     ALTER TABLE departures ADD CONSTRAINT departures_class_id_fkey
       FOREIGN KEY (class_id) REFERENCES classes(id) DEFERRABLE;
     ALTER TABLE students ADD CONSTRAINT students_class_id_fkey
       FOREIGN KEY (\"classId\") REFERENCES classes(id) DEFERRABLE;
     -- On rename: INSERT new class row, UPDATE students and departures (cascade),
     -- SET retired_at on old class row.

   Recommendation: Option A for immediate safety, Option B as the long-term goal.
   The sync function must detect renames: when a class disappears from the sheet
   AND a new class appears in the same grade with close student count, treat it
   as a rename and call rename_class(), not delete + insert."

PART XI — WHAT "INFRASTRUCTURE STRONG ENOUGH TO CHANGE" ACTUALLY REQUIRES
================================================================================

The user asked specifically: "I want an infrastructure strong enough that I can
change things and still nothing will break."

The layered refactor (Domain → Services → API) is necessary but not sufficient.
The infrastructure will bend without breaking only if these six properties hold:

PROPERTY 1: Entities are first-class in the data model
  Today supervisors are PINs in a key-value table. Classes are strings with no FK.
  When entities are not rows, you can't query them, can't join them, can't enforce
  constraints about them, can't add attributes to them.
  Required: supervisors table, classes table (or at minimum a classes-as-FK pattern).

PROPERTY 2: Side effects are registered, not hardcoded
  Today push notification, audit write, status change are hardcoded sequences.
  When effects are registered (domain events + subscribers), you add a new effect
  in one place with zero changes to existing code.
  Required: domain event system (Directive D13).

PROPERTY 3: Configuration is data, not code
  Today 7+ business-critical values are compile-time constants.
  When configuration is in app_settings, admins can change behavior without
  touching code. Developers can override per environment.
  Required: runtime config service (Directive D14).

PROPERTY 4: Both implementations of the interface are faithful
  Today mockClient diverges from supabaseClient in 5 critical ways.
  When the contract is enforced by tests, every change to one automatically
  requires the equivalent change to the other.
  Required: contract tests (Directive D16).

PROPERTY 5: Entity changes have migration paths, not just migration scripts
  Today a class rename silently corrupts quota counts. An idNumber correction
  destroys student history. These need application-level migration RPCs, not
  just DB migrations — because the application has denormalized data that must
  also be updated.
  Required: rename_class(), correct_student_id_number(), and a documented
  process for "how do I make a data correction safely."

PROPERTY 6: The system can be tested at every layer
  Today there are 3 test files, 9 tests, for a 15,000-line codebase. Zero tests
  for the sync engine, GPS, push, realtime, quota, or any admin page.
  When every layer has tests (domain: unit, services: integration, API: contract,
  SQL: pgTAP), a change in one layer fails the tests for that layer immediately.
  Required: the test strategy Codex has in Phase 11 must be moved to Phase 0
  (baseline tests) and Phase 3/4/5 (tests per layer). Phase 11 cannot be
  "write all tests at the end" — tests written after the code is already running
  are documentation, not safety nets.
